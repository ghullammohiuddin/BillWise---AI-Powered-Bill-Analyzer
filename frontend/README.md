# BillWise frontend

Full implementation of all 8 required screens (handoff Section 3), wired to the
locked API contract (Section 5). Fills in every file from the `feat(frontend):
initialize full frontend project` scaffold commit, plus a small number of
additions listed below.

## Run it

```bash
npm install
cp .env.local.example .env.local   # point at your backend, defaults to localhost:3001
npm run dev
```

Visiting `/` redirects to `/bills` (the Dashboard).

## Architecture

Client components + hooks (`useBills`, `useBillDetail`, `useComparison`,
`useBillQA`, `useUploadBill`) doing `fetch` in `useEffect`/`useState` — no
React Query/SWR, matching the stack list in the handoff doc exactly. Each
hook returns `{ data, isLoading, error, refetch }` (or the equivalent for its
screen), and pages render `LoadingState` / `ErrorState` / `EmptyState` off
that, per handoff principle 4 (every async action needs a state).

## Files added beyond the original scaffold

The scaffold didn't include a `components/ui` folder, even though
`components.json` (shadcn config) was part of it — shadcn primitives are
normally generated by its CLI, not hand-scaffolded. Since `components.json`
declares `"ui": "@/components/ui"` as its alias, that folder is real
infrastructure the app needs to run, not optional:

- `src/components/ui/{button,card,badge,skeleton,alert,input,label}.tsx` —
  hand-written in the shadcn/ui style (not CLI-generated). Swap with
  `npx shadcn@latest add ...` if you want the canonical versions; class names
  and props should be compatible since `components.json` is already
  configured for it.
- `src/lib/utils.ts` — the `cn()` classname helper shadcn's `components.json`
  expects at `@/lib/utils`. Coexists fine with the `src/lib/utils/` folder
  already in the scaffold (`formatCurrency.ts`, `formatDate.ts`) — Node/TS
  module resolution tries the exact file `utils.ts` before ever looking
  inside a same-named directory, so there's no import ambiguity.
- `postcss.config.js`, `.gitignore`, `.env.local.example` — standard project
  plumbing not in the original 56-file list.

Everything else fills an existing scaffold file at its original path — nothing
was renamed or restructured.

## Four contract/scaffold gaps I flagged rather than papered over

**1. Per-bill "+X%" badge on the Dashboard isn't in the API.**
`GET /bills` (Section 5) returns `totalAmount` per bill but no per-item delta,
even though Section 3.3 asks for one. `BillList.tsx` derives a display-only
delta by comparing each bill's `totalAmount` to the next one chronologically —
real backend data, just compared client-side. It's separate from, and can
drift slightly from, the authoritative `comparison` object on
`GET /bills/:id/comparison`, which is what the Comparison screen uses and
should always win if the two disagree. One-line ask to backend if you want
them to match exactly: expose the delta on the list endpoint.

**2. `src/app/bills/[id]/review/page.tsx` can't host the real Extraction
Review screen.** Section 3.2 is explicit that review happens *before* a bill
is saved, and Section 5's upload flow only returns a bill `id` from the final
`POST /bills` call — so there's no id yet at review time. The scaffold's
`[id]/review` route structurally can't work for this. The real review step
lives in `/upload` instead (`ExtractionForm`, rendered during
`useUploadBill`'s `'review'` step); `[id]/review/page.tsx` is just a redirect
to `/bills/[id]` so an old link to it doesn't 404. This was very likely a
scaffolding-tool artifact — an automated generator inferring a plausible route
from the screen name without cross-checking the upload flow's sequencing. You
may want to just delete that route.

**3. No way to know "low confidence" at comparison-view time.** Section 3.6
wants a disclaimer when the backend flags low-confidence data, but
`confidence` only appears in the `POST /bills/extract` response (Section 5) —
it's not part of the persisted `Bill` schema or the comparison response.
`AIExplanationPanel` accepts an optional `lowConfidence` prop for this, but
the Comparison page currently has no data source to pass it, so it's left
unset. Wire it up if backend ever adds `confidence` to `GET /bills/:id` or the
comparison response.

**4. Dashboard colors use `DESIGN.md`'s prose, not its YAML frontmatter.**
The Stitch-exported `DESIGN.md`'s YAML token block looks like a dark-scheme
palette (dark "container" colors paired with light "on-container" text)
mapped onto a light `background`/`surface` — likely an export quirk. Its
prose section gives unambiguous hex values for a normal light scheme (Deep
Teal `#0B5351`, Soft Mint `#2A9D8F`, Coral `#E76F51`, etc.), which is what
`tailwind.config.ts` uses. Worth a quick visual diff against the live Stitch
preview if pixel-parity matters for the demo.
